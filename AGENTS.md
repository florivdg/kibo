# Kibo

Kibo ("Kita Board") is a digital notice board for Kitas (German daycare centres): Kita admins create boards that parents and other visitors open via a link and post on.

Astro (Node adapter, SSR) + Vue 3 + Tailwind 4. UI language is German. Package manager: Bun.

- `src/pages/admin/` – admin panel built with shadcn-vue (`src/components/ui/`, managed via `bunx shadcn-vue@latest add …`, don't hand-edit) and admin components in `src/components/admin/`. Styles: `src/styles/global.css`.
- `src/pages/` (non-admin) – custom frontend, no shadcn. Styles: `src/styles/frontend.css`.
- Use the `@/` alias for imports from `src/`.
- User-facing German says "Brett"/"Bretter", never "Board"; code, URLs and identifiers keep `board`.
- Each Kita is a better-auth organization with two roles (`src/lib/organization-roles.ts`): whoever creates it is its `owner`, everyone invited is an `admin`. Both manage boards and notes (`/admin/boards`; the `boards.*` actions only ask for a membership); only the owner invites, withdraws invitations, removes members and renames the Kita, an admin can leave. Each Kita has one public link, `/k/<kitaToken>/` (table `kita_link` in `src/db/schema/`, one row per organization, cascades with it; 22 base64url characters, so a malformed token never reaches the database; created the first time an admin page reads it, `kitaLinkOf` in `src/lib/board/kita-link.ts`, which also gives the Kita's name, or when the owner saves the privacy contact; the row also holds that contact, `privacy_contact`, kept across renewals): the Kita page lists every board (name, description, current note count, a „Neu“ marker from the newest note's `createdAt` against when this device last opened the board, kept in localStorage `kibo:seen`; a bell per board). Browser storage is written only when there is something to keep (`useDeviceRecord` in `src/composables/use-device-record.ts`: null until then, null removes the entry — § 25 TDDDG): `kibo:seen` once a board was opened, `kibo:own-notes` (delete keys by note id, `src/composables/use-own-note-keys.ts`, `liveOwnNotes` in `src/lib/board/own-notes.ts`) once a note is pinned, pruned of expired notes on the first read and every write and removed when empty. A board is at `/k/<kitaToken>/<boardId>/` (`src/pages/k/[kita]/`; the board id is no secret, every lookup checks the board belongs to the token's Kita, another Kita's board answers like an unknown one: under a working Kita link a 404 „Dieses Brett gibt es nicht (mehr).“ with a link to the Kita page, `findBoardPage` in `src/lib/board/queries.ts`); generated links always end with `/`. An unknown or renewed link gets one 404 page („Diesen Link gibt es nicht (mehr) …“, `src/pages/404.astro` for every path under `/k/`); the middleware redirects a `/k/` address without the trailing slash (308, query kept, files like the manifest excepted). Any visitor can post notes; notes expire after 7/14/30 days. Renewing is per Kita and open to every member (`boards.renewKitaLink`, a „Kita-Link“ card on `/admin/boards` with QR code, copy, open, „Neuen Link erzeugen“): new token and every push subscription of the Kita's boards deleted in one transaction, then `pushDispatcher.cancel` for every board of the Kita; notes stay. A board's admin page shows „Link zu diesem Brett“ (copy, QR code, no renewal). There are no board tokens and no per-board renewal. Only with `HOSTED` (the Kita is the controller of its boards, the operator its processor): the foot of every page of a working Kita link — Kita page, board pages, a paused Kita's (`KitaPaused.astro`) and an unknown board's page, not `UnknownLink` — says „Verantwortlich für die Bretter: <Kita>“ above the legal links, plus „Fragen zum Datenschutz:“ with the Kita's privacy contact if set (`responsible` from `kitaResponsibility` in `queries.ts`, read with the link in the same statement, undefined without `HOSTED`; `BoardLayout`/`PageNotice` → `Frontend.astro` → `LegalFooter.astro`). The contact (`src/lib/board/privacy-contact.ts`, shared with the form: one e-mail address ≤ 254, shown as `mailto:`, or an `https://` link with a dotted host and no credentials ≤ `PRIVACY_CONTACT_MAX` (300), plain text without whitespace, empty = none) is set by the owner only via `kita.setPrivacyContact` (`src/actions/kita.ts`, session verified by the middleware for `kita.*`; 404 without `HOSTED`, 403 for an admin, `BAD_REQUEST` with the form's sentence, never blocked by a pause) on `/admin/kita` (`PrivacyContactSettings.vue`, read-only for admins, absent without `HOSTED`). Tests: `tests/kita-privacy-contact.test.ts`; documented in `docs/fuer-kitas/team.md`.
- Data export of a Kita (EU Data Act switching, return of data under the AVV): `GET /admin/kita/export` (`src/pages/admin/kita/export.ts`, under `/admin` so the middleware's session guard applies) answers the active Kita as one JSON attachment (`kibo-<slugBase of the name>-<Berlin day>.json`, `slugBase` in `src/lib/organization-slug.ts`) for any member — owner and admins alike (`isMember` asked again, else 404 with no data) —, also while the hosted instance has paused the Kita, within its budgets (`allowKitaExport`: `KITA_EXPORT_ACCOUNT_BUDGETS` per account first, then `KITA_EXPORT_KITA_BUDGETS` per Kita, which only counts what passed the account's; a request whose `Sec-Fetch-Site` is present and not `same-origin` gets the 403 refusal before anything is counted; 429 with `Retry-After`, 503 when unverifiable). `kitaExport` in `src/lib/board/kita-export.ts` reads in one read-only repeatable-read transaction `{ format: 'kibo-kita-export', version: 1, exportedAt, kita: { name }, boards: [{ id, type, typeLabel, categories, name, description, pushEnabled, createdAt, updatedAt, notes: [current notes, newest first: id, categoryId, title, body, author, contact|null, createdAt, expiresAt] }] }` — never the Kita link, delete-key hashes, push subscriptions, report cases, members, invitations or the subscription. The format is the public register (Data Act Art. 26) in `docs/selbst-hosten/datenexport.md`, field by field; any change to it needs a new `version` there and in the code. The „Daten exportieren“ card (`KitaExportCard.vue`) on `/admin/kita` fetches it (`src/lib/board/kita-export-client.ts`, `redirect: 'manual'`, refusals as toast). Kitas read `docs/fuer-kitas/datenexport.md`. Tests: `tests/kita-export.test.ts`.
- Board types (fixed categories and colours) live in `src/lib/board/board-types.ts`. Server reads in `src/lib/board/queries.ts`; all mutations are Astro actions in `src/actions/` (`boards.*` and `reports.*` check the session themselves, `notes.*` is public).
- Reported notes (`src/lib/reports/`, schema `src/db/schema/report.ts`): `notes.report` (public; `kitaToken` and `boardId`, note id, reason from `REPORT_REASONS` in `types.ts`, optional remarks ≤ 500, honeypot) checks the network budget before the board lookup, then network+board and network+note, and in one transaction reads the note itself (`reportedNote`: on this board, not expired — an old Kita link or another board's note answers 404), counts the board budget and files the report (`fileReport` in `mutations.ts`): one open case per note (partial unique index, an upsert, so parallel reports make one case), a server-side copy of the note (`noteId` is set null when the note goes; board/Kita deletion cascades), at most `REPORTS_PER_CASE_MAX` report rows (identical remarks per note stored once, `claimReportRemarks`), no reporter identity. A paused Kita's board refuses it like `notes.create`. With `operator` (`{ name?, email?, goodFaith: true }`; the option „Rechtswidriger Inhalt – auch an den Betreiber melden“ in `NoteReport.vue`, offered and accepted only while `operatorDetails.email` is set — always on the hosted instance —, `operatorReportAddress()`) the report is also a DSA Art. 16 notice (`src/lib/reports/operator-notice.ts`): same case for the Kita, `REPORT_OPERATOR_BUDGETS` (per note 5/day, per board+link 20/day) counted in the same transaction (over them the whole report is refused, it can go without the option), and after the commit a mail to `OPERATOR_EMAIL` (`operatorReportMail`: Kita, board, board URL, note id, reason, remarks, the note copy, notifier name/e-mail, the good-faith statement, the `remove-note` call) — one per such report, not deduplicated like the team's — then, only if that mail was handed to SMTP and within the `report-receipt` mail budgets per recipient (`allowAuthMail`), a fixed-text receipt to the notifier's address (`operatorReportReceiptMail`, echoes nothing anyone typed); the action answers `{ operatorNotified, receiptSent }` (`sendOperatorReport`'s `{ sent, receiptSent }`; `receiptSent` is `false` without an address, over the budget or when that mail failed) and the form tells the visitor to write to the operator if `operatorNotified` is `false`, and promises a confirmation only if `receiptSent`. Name and e-mail of the notifier are in that mail only, never in the database; `operatorReportMails.send` is the test seam (`tests/operator-reports.test.ts`). The operator takes a note down with `remove-note` (`removeNoteAsOperator` in `src/lib/reports/takedown.ts`, no `@/db`: checks `--id` is a UUID before any query, locks the note `FOR UPDATE`, closes its open case as `removed` with `closedByOperator` and no `closedBy` — or, without one, re-marks the newest case the Kita closed (it kept the note) the same way —, then deletes the note, answering `reportCase: 'closed' | 'updated' | 'none'`; `ClosedCaseCard` says „vom Betreiber“). Only a new case writes outbox rows (`report_notification`, one per owner/admin at that moment) in the same transaction; `outbox.ts` works them off right after the commit (`reportMailer.schedule`) and in a 5-minute sweep started by `runtime.ts`: claim per Kita and recipient in a short transaction under `pg_advisory_xact_lock` on the pair, taking nothing while another run holds a row of the pair (so parallel processes can't send a second mail within the hour), 15-minute lease, the clock (`clock` option, injectable for tests) read afresh for each claim, throttle check and completion; re-check the membership (`skipped` otherwise) and that the case is still open, at most one mail per recipient and Kita per `REPORT_MAIL_INTERVAL_MS` (later cases are postponed and announced together, not dropped), retries after 5/15/60/240 min then `failed`, built on `sendMail`'s boolean; `noteReportMail` in `templates.ts` (subject „Kibo: Neuer gemeldeter Zettel“, no note text or remarks, link to `/admin/reports/<id>` or `/admin/reports?kita=<id>` from `paths.ts`). Admin: `/admin/reports` and `/admin/reports/[id]` (`src/components/admin/reports/`, „Meldungen“ in the sidebar with the open count), reads in `queries.ts` scoped to the active Kita; a link for another Kita the user handles reports in switches the active Kita (`caseAccess`/`kitaAccess` in `access.ts`, `settleAccess` in `page-access.ts`), anything else is 404. `reports.close` (`src/actions/reports.ts`) asks for an owner/admin membership of the active Kita and closes with or without deleting the note in one transaction (`closeCase`: reads the case, locks the note `FOR UPDATE` before touching the case — the order `notes.report` uses, so the two can't deadlock —, then deletes it and writes the resolution: `removed` only if the note was actually deleted, else `kept`) — never blocked by a paused Kita. The overview lists the newest `CASE_LIST_LIMIT` (200) cases per status with the real count (`listCases` returns `{ cases, total }`) and says when it shows fewer. Retention: closed cases go `REPORT_CLOSED_RETENTION_DAYS` (30) after closing, every case `REPORT_MAX_RETENTION_DAYS` (90) after the first report (`purgeReportCases`, hourly); both in `src/lib/limits.ts`. Tests: `tests/note-reports.test.ts`, `tests/report-outbox.test.ts` (helpers in `tests/helpers/reports.ts`, which stops the app's mailer; runs use `only`). Documented in `docs/fuer-kitas/meldungen.md`, `docs/selbst-hosten/spam-schutz.md#meldungen`, `docs/selbst-hosten/betrieb.md` and, for the operator's duties (Art. 16–18), `docs/selbst-hosten/rechtswidrige-inhalte.md`.
- Spam protection for the public actions, the auth mails, the invoice requests of the hosted instance and its start-page view counting lives in `src/lib/spam/` (IP normalisation — IPv6 per /64, for posting and reporting also per /56 and /48, each wider network counted only for what passes the narrower network’s budgets —, multi-stage budgets and duplicate detection, all counted in Postgres); the rules are documented in `docs/selbst-hosten/spam-schutz.md`. The per-board budgets of `notes.create`/`notes.report` are keyed by board and current Kita token, the per-Kita budget of `notes.create` by the Kita token (`boardBudgetKey`/`kitaBudgetKey` in `src/lib/board/kita-link.ts`), so renewing the Kita link resets them. `notes.create` needs a form token from `notes.formToken` (`form-token.ts`: `<key id>.<issue time>.<nonce>.<HMAC over board id, time and nonce>`, verified with exactly the named live key — only an unknown key id re-reads the keys, at most every 5 s per process (`refreshKeys` in `store.ts`) —, nothing stored; taken 3 s to 2 h after issue, `NOTE_FORM_TOKEN_*` in `src/lib/limits.ts`, otherwise `BAD_REQUEST` like the honeypot); the composer fetches it on opening and waits out or renews it (`src/lib/board/form-token-client.ts`). Board notes are read one page at a time (`notePage` in `src/lib/board/queries.ts`).
- Tests are `bun test` files in `tests/`; they use the local Postgres from `bun run db:up`. `tests/preload.ts` stands in for Astro's virtual modules: `astro:env/server`, and `astro:actions` (`tests/helpers/astro-actions.ts`), so the real actions run as `action.orThrow.call(context, input)` with a context from `tests/helpers/actions.ts`.
- Postgres via Drizzle: schema in `src/db/schema/`, migrations in `drizzle/` (generated, don't edit). Server env vars are declared in `astro.config.mjs` and read via `astro:env/server`.
- Auth: better-auth (email/password, organization, TOTP two-factor, passkeys via `@better-auth/passkey`). Options that affect the schema live in `src/lib/auth-options.ts`; `src/middleware.ts` guards `/admin`. A passkey sign-in replaces password and TOTP, so user verification is required on both ceremonies (`authenticatorSelection` with `residentKey`/`userVerification: 'required'`, and enforced on the server, since the plugin itself only asks for `preferred`: `afterRegistration`/`afterAuthentication` in `src/lib/passkeys/rules.ts`, the plugin's `afterVerification` hooks, throw `PASSKEY_USER_VERIFICATION_REQUIRED`; `afterAuthentication` also refuses an account whose address isn't verified, 403 `EMAIL_NOT_VERIFIED`, like the password login). Adding one (account page, card `src/components/admin/PasskeySettings.vue`, list server-rendered by `listPasskeysOf`; `countPasskeysOf`/`deletePasskeysOf` beside it in `src/lib/passkeys/queries.ts`) asks for the current password: `checkPasskeyRegistration`, the before hook on `POST /passkey/verify-registration` in `src/lib/auth.ts`, reads `password` from the body and verifies it (`INVALID_PASSWORD`), an optional `name` (plain text, ≤ `PASSKEY_NAME_MAX` 60, `INVALID_PASSKEY_NAME`) and the cap `PASSKEYS_PER_ACCOUNT` (10, `PASSKEY_LIMIT_REACHED`; both in `src/lib/limits.ts`); without a session it steps aside. The plugin's `addPasskey` can't carry a password, so `src/lib/passkeys/register-client.ts` runs the ceremony itself (`/verify-password` first as a UX check, `startRegistration` from `@simplewebauthn/browser`, never a `name` query — the plugin would make it the WebAuthn user name). Sign-in on the login page through `src/composables/use-passkey-sign-in.ts`: conditional UI (autofill on the e-mail field, `autocomplete="username webauthn"`) when the browser offers it, and the button „Mit Passkey anmelden“; it never leads to `/admin/two-factor`. The plugin's `signIn.passkey` isn't used: `src/lib/passkeys/sign-in-client.ts` runs the steps itself (options, `startAuthentication` with `userVerification: 'required'` set on the client, since the plugin asks for `preferred` — the server check stays —, verify; requests for options are serialized there, since the plugin keeps one challenge cookie per browser and the last answer owns it — a suggestion's late answer can't replace the button's challenge), and a suggestion that was replaced stays quiet (a generation counter). The shared `authClient` has no `passkeyClient()`, which would bundle `@simplewebauthn/browser` into every page using it; removing a passkey is a plain `$fetch` to `/passkey/delete-passkey`. The suggestion starts again after every outcome that stays on the page (at once after a server answer, after `SUGGESTION_RETRY_MS` 5 s when the browser ended it) and an idle page refreshes it every `SUGGESTION_REFRESH_MS` (4 min), before the plugin's 5-minute challenge expires. Removing asks for confirmation only. A password reset deletes every passkey of the account (`onPasswordReset`), changing the password keeps them. `src/lib/passkeys/transactions.ts` wraps registration, passkey authentication and the core password-reset endpoint in transactions with the same user-row lock; registration re-reads the session and re-checks the password and cap after taking the lock. Reset atomically updates the password, consumes the token, deletes passkeys and revokes sessions; an overlapping registration or passkey sign-in cannot survive it. The app-side queries use the request-scoped `passkeyTransaction` executor, including the initial Kita lookup when creating a session. `credential_id` is unique (the plugin and `afterAuthentication` look a passkey up by it; `withUniqueCredentialId` in `authPlugins` extends the plugin's schema, since its `schema` option can only rename). `rpID` and `origin` come from `BETTER_AUTH_URL` (another domain makes existing passkeys unusable). `/passkey/update-passkey` and `/passkey/list-user-passkeys` are in `disabledPaths` (404); `verify-registration`/`verify-authentication` have the guessing rule of the login, the two `generate-*-options` routes 20 per minute. Tests: `tests/passkeys.test.ts`, `tests/passkey-sign-in.test.ts`.
- Kita rules live in `src/lib/organization-rules.ts` (name/slug validation in the create/update hooks; a name may not read like a link, since invitation mails carry it) and `src/lib/limits.ts` (at most 3 Kitas per account — counted as the Kitas it owns, by the `organizationLimit` function in `src/lib/auth.ts`, so memberships by invitation don't count; the hosted instance counts by the subscription instead, see below — 10 members and 10 pending invitations per Kita); unused organization routes are in `disabledPaths` in `src/lib/auth-options.ts` and answer 404.
- Invitations (`/admin/kita`, owner only): `/organization/invite-member` runs through `checkInvitationRequest` in `src/lib/auth.ts` first (role `admin` only, the domain list, no link-like Kita name — the backstop for names older than that rule —, budgets per Kita and per owner in `src/lib/spam/`; it steps aside for anyone who isn't the owner), the mail goes out like the other auth mails (`invitation` budgets per recipient) with a 7-day link to `/admin/invitation?id=…`. That page (`src/lib/invitation-view.ts`) renders with and without a session, shows a guest only the Kita's name and grants no session; accepting takes the normal login. Members and pending invitations are read on the server (`src/lib/organization-members.ts`), so Better Auth's list routes stay off. Someone who signs in without a Kita but with a pending invitation lands on the invitation (`src/middleware.ts`). Free text is checked by `src/lib/plain-text.ts` (no control/bidi characters, something visible; its patterns are defined in `scripts/instance-config.mjs`, which holds `HOSTED_PRICE_NOTE` to the same ones and can't import from `src/`); actions use `requiredText`/`optionalText` from `src/actions/text-fields.ts`.
- What an instance is set up to be is read once in `src/lib/instance.ts`: who may sign up — `SIGNUP_MODE=open|closed` and `SIGNUP_EMAIL_DOMAINS` (exact domains and `*.` wildcards for subdomains) — and whether it is the hosted instance (`HOSTED=true|false`, the object `instanceMode`; it switches on `/docs` and the subscriptions below, with `hostedPricing` from `HOSTED_PRICE_EUR`, `HOSTED_INCLUDED_KITAS`, `HOSTED_EXTRA_KITA_EUR` and `HOSTED_TRIAL_DAYS` — whole numbers, defaults 49/3/10/30 — and `hostedContact` from `HOSTED_TERMS_VERSION` — letters, digits, `.`, `-`, `_`, at most 64, since it is part of `/agb/<version>` — and `HOSTED_OPERATOR_EMAIL`, both required with `HOSTED=true`). `docsHref()` is where the admin sidebar's „Hilfe“ link leads: `/docs` when hosted, otherwise `DOCS_URL` (default: the docs folder on GitHub). The parser is `scripts/instance-config.mjs`, plain ESM without dependencies, shared by the start-up check in `scripts/server.mjs`, the app and `scripts/admin.ts`. The rules the auth hooks apply are in `src/lib/signup-rules.ts`, bound to `/sign-up/email` and `/change-email` in `src/lib/auth.ts` before Better Auth touches the database, so a rejection says nothing about whether an account exists. Closed, `/admin/signup` redirects to the login and the sign-up links are not rendered — except for someone invited to a Kita: `/admin/signup?invitation=<id>` renders for a pending invitation, and the sign-up passes when its body carries that id and the invited address. The id is the capability; nothing is looked up by address, and every miss answers `SIGNUP_CLOSED`. Who runs the instance is `operatorDetails` (`OPERATOR_NAME`, `OPERATOR_ADDRESS`, `OPERATOR_EMAIL`, `OPERATOR_LEGAL_INFO`; address and legal info are lines separated by `|`, held to the plain-text patterns, no links in name and address; separate from `HOSTED_OPERATOR_EMAIL`, the invoice mailbox), and `IMPRESSUM_URL`/`DATENSCHUTZ_URL`/`AGB_URL`/`AVV_URL` must be `https://` addresses when set (`parseLegalUrl`, which `legalUrl` in `src/lib/legal.ts` applies to all four). The settings are objects (`signupPolicy`, `instanceMode`, `hostedPricing`, `hostedContact`, `hostedPriceNote`, `sourceLink`, `analytics`, `operatorDetails`), which tests change in place.
- The start page (`src/pages/index.astro`) is the same on every instance down to the four feature notes. With `HOSTED=true` it adds the service's sections (`src/components/marketing/`, plain Astro in the shell `Section.astro`; visible text and JSON-LD come from `src/lib/marketing/hosted-page.ts`, which imports no server code, tested in `tests/marketing-page.test.ts`) and page views of `/` are reported to Plausible server-side (`src/lib/analytics/pageview.ts`, never delays or changes the page, `tests/analytics.test.ts`). Without `HOSTED` the page must stay byte-identical — the markup above the sections is not to be reformatted. Photos with sizes are listed in `src/lib/images/responsive.ts` (`bun run images` makes the committed `<name>-<width>.webp` files, `src/lib/images/image-service.ts` points the srcset at them; tests `tests/image-sizes.test.ts`, `tests/responsive-images.test.ts`). The tone there is „ihr“/„eure Kita“; the admin area says „Sie“.
- Kibo is AGPL, so `LegalFooter.astro` (its links are `LegalLinks.astro`) links „Quelltext“ with the version from `package.json` (compiled in, `sourceLink` in `src/lib/instance.ts`) on every instance; `SOURCE_URL` (http/https, default `REPOSITORY_URL`) points it at the source of a changed version (§ 13).
- The hosted instance (`HOSTED=true`) is the project's own service, not meant for self-hosting and not documented in `docs/` (its operator documentation is kept outside this repository). It bills accounts, not Kitas: `src/lib/hosted/` — the state is computed, never stored (`state.ts`), enforcement in `access.ts` (a paused Kita is refused with `PAYMENT_REQUIRED` via `src/actions/kita-access.ts`; taking a note down, closing reports and the data export always work), reminders and deletion in `reminders.ts`, versioned terms in `terms.ts`, the subscription page `/admin/abo`; table `hosted_subscription` (exists everywhere, empty without `HOSTED`). Without `HOSTED` nothing there touches the database; reads never write; a database error propagates, never fail-open. `subscriptions.ts` and `billing.ts` take an explicit `on: Executor` and must not import `@/db` (the operator's script uses them). Tests: `tests/hosted-*.test.ts`, `tests/legal-terms.test.ts`; runs of reminders and deletion take `{ on, send, only }` and must never delete real Kitas of the local database.
- `scripts/admin.ts` is the operator's CLI; each command is an entry in `COMMANDS` and a file under `scripts/admin/`: `create-user` (for a closed sign-up: a verified account, password from a hidden prompt or stdin, never an argument, same name/password/domain rules as the sign-up), `remove-note --id …` (takes a note down on a notice of illegal content and closes its open case, see reported notes) and the hosted mode's commands (`subscriptions`, `kitas`, `invoice`, `set-paid`, `set-free`, `hold-deletion`, `delete-kitas`). `bun run build` bundles it to `dist/admin.mjs`, which is how it gets into the image; it uses drizzle with the app's schema on its own `pg.Client` (`Database`/`Executor` in `src/db/types.ts`) and must not import anything that loads `astro:env` — so never `@/db`. Locally: `bun run admin …`.
- Security headers: the page CSP is `security.csp` in `astro.config.mjs` (Astro hashes its inline scripts/styles; `img-src 'self' data:`), everything else (CSP for non-pages, X-Frame-Options, nosniff, Permissions-Policy, COOP, Referrer-Policy, X-Robots-Tag, no-store) comes from `src/lib/server/security-headers.ts` via the middleware; `/k/…` (Kita page, board pages, manifest) gets `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` and `Cache-Control: private, no-cache`. HSTS and headers for static `/_astro/*` are the proxy's job.
- Signing up requires confirming the e-mail address: it creates no session, and the link from the mail only unlocks the login (it deliberately grants no session of its own, so a mailbox can't skip the password and TOTP). The same holds for the account page (`/admin/account`, reachable without a Kita): an address change is confirmed from the old address first, then verified from the new one, and a `hooks.before` in `src/lib/auth.ts` turns the final link away unless the browser is already signed in; deleting the account always asks for the password, and the Kitas the account owns go with it, admins or not (`rememberOrganizationsOf`/`deleteOwnedOrganizations` in `src/lib/organization-access.ts`, the account page warns); an admin's deletion only ends their membership. After signing in, someone without a Kita lands on a pending invitation if there is one, otherwise on `/admin/organizations/new`. Mails go out via nodemailer (`src/lib/mail/`); every template goes through `render()` in `templates.ts`, which ends each mail, HTML and text, with the footer of `footer.ts` (`mailFooter()`: the operator details that are set, then absolute links to Impressum and Datenschutz — `absoluteLegalHref` in `src/lib/legal.ts`: `IMPRESSUM_URL`/`DATENSCHUTZ_URL` or `BETTER_AUTH_URL` + `/impressum`, `/datenschutz`; all configurable text HTML-escaped), so a new mail gets it by using `render()`; the invitation adds `invitationNotice()` (the Kita's owner entered the address to invite to help run the Kita; who is responsible depends on `instanceMode.hosted` — hosted: the Kita, with the operator processing on its behalf under the AVV; otherwise only the operator, named as the contact, with no AVV claimed —; kept until answered/withdrawn/expired after 7 days and purged by the hourly run, `OPERATOR_EMAIL` for unwanted invitations, link to the privacy policy). `detailText`/`MailDetail` live in `details.ts` without dependencies, because `scripts/admin/invoice.ts` prints them and must not load the templates; without `SMTP_HOST` the dev server writes them to the log, links included, while a production build logs an error instead — confirmation and reset links must never end up in production logs. Encryption is explicit in `src/lib/mail/transport-options.ts` (implicit TLS on 465 or `SMTP_SECURE`, STARTTLS required otherwise, plaintext only with `SMTP_ALLOW_INSECURE` for Mailpit).
- `scripts/server.mjs` refuses to start on a bad configuration (missing `DATABASE_URL`/`BETTER_AUTH_URL`/`BETTER_AUTH_SECRET`, secret under 32 chars, non-https URL outside localhost, invalid `TRUSTED_PROXIES`, `SIGNUP_MODE`, `SIGNUP_EMAIL_DOMAINS`, `HOSTED`, `DOCS_URL`, `SOURCE_URL` or `HOSTED_*` number, `HOSTED_TERMS_VERSION`, `HOSTED_OPERATOR_EMAIL`, `HOSTED_PRICE_NOTE`, `PLAUSIBLE_DOMAIN` or `PLAUSIBLE_URL`, an `OPERATOR_*` value, `IMPRESSUM_URL`, `DATENSCHUTZ_URL`, `AGB_URL` or `AVV_URL`, `HOSTED=true` without those two or without `OPERATOR_NAME`/`OPERATOR_ADDRESS`/`OPERATOR_EMAIL`, without `SMTP_HOST` or without imprint, privacy policy, terms and data processing agreement as `IMPRESSUM_URL`/`DATENSCHUTZ_URL`/`AGB_URL`/`AVV_URL` or `impressum.md`/`datenschutz.md`/`agb.md`/`avv.md` in `LEGAL_DIR` (`hostedLegalProblems`; every mail links the first two) — the mail server and the files only here, the dev server logs its mails and shows a page without a file; tested in `tests/server-config.test.ts`) and, right after starting the server, imports the bundled middleware so `runtime.ts` starts with the server rather than with the first request — a module that fails to load (the terms check) ends the process with 1 (tested in `tests/server-config.test.ts` against a stand-in build).
- `src/lib/server/runtime.ts` is the server's start-up hook, imported for its side effects by `src/middleware.ts`: first, on the hosted instance, a top-level `await storeTermsVersion()` (see the versioned terms above); SIGTERM drains the HTTP server and then closes the pg pool, an hourly timer purges expired notes, expired sessions, expired `verification` rows (`purgeExpiredVerifications` in `src/lib/expired-sessions.ts`; Better Auth removes expired rows only when reading them, so unused passkey challenges and 30-day two-factor `trust_device` rows would stay), Better Auth's `rate_limit` rows (`IP|path` in clear) whose last request is older than the longest configured window plus 5 minutes (`purgeStaleRateLimits`, same file, `LONGEST_RATE_LIMIT_WINDOW_MS` read from `authOptions`: Better Auth itself only prunes when a later request opens a new window), push subscriptions that keep failing or are idle (`purgeStaleSubscriptions`, see web push), week-old unverified accounts without a Kita, invitations that are expired or answered and reported-note cases past their retention, starts the outbox sweep for report mails (`src/lib/reports/outbox.ts`, drained on SIGTERM), drops expired spam counters, writes the spam tally to the log and, on the hosted instance, starts the subscriptions of owners who have none, sends the subscription reminders, deletes the Kitas of accounts that expired 90 days ago and Kitas nobody owns (`src/lib/hosted/reminders.ts`), and the sign-up, the instance mode, the SMTP setup and the operator details are logged once (`logOperatorConfiguration` in `src/lib/mail/footer.ts` warns about missing `OPERATOR_*` and about an Impressum or Datenschutz page with neither URL nor file, `isLegalPageFilledIn` in `src/lib/legal.ts` — only possible self-hosted or in dev). `/api/health` answers 200 only when the database answers.
- Web push for new notes (optional, off without `VAPID_*`) lives in `src/lib/push/`: RFC 8291/8292 on Web Crypto without a dependency, the endpoint allow-list, the subscription rules behind the public `push.*` actions, and the dispatcher that `notes.create` schedules after its commit (2 min debounce per board in memory, throttled via `push:board-hour`). One push subscription per browser or installed app, stored per board (`push_subscription`, `unique(boardId, endpoint)`): `push.sync({ kitaToken, seen?: { boardId, until }, endpoint, keys })` returns the board ids of every subscription the endpoint has on the Kita's push-enabled boards and refreshes the keys where they changed (the bell states, one sync per page load; it never adds one), noting the visit in `lastVisitAt` at most once a day in the same conditional `UPDATE` (scoped like the bells; `push.subscribe` sets it too), `push.subscribe`/`push.unsubscribe` take `{ kitaToken, boardId, endpoint … }`; `push.unsubscribe` and `push.sync` also answer `remaining` — whether the endpoint still has a subscription on any board of the instance (`followsAnyBoard`; any Kita, push-enabled or not: one worker and endpoint serve them all) — and when it doesn't, `usePushBells` calls `PushSubscription.unsubscribe()` and shows 0 on the icon (`afterUnsubscribe`/`afterSync` in `src/lib/board/push-client.ts`), so the pages stop syncing: after the last bell switched off, and on the next sync once the server dropped the rows (renewed link, notifications switched off, board deleted, purged); a `push.unsubscribe` that answers `NOT_FOUND` is followed by one `push.sync` without `seen` (a renewed link answers `NOT_FOUND` again and the subscription stays); errors and unknown answers never end it; every browser+server change of the shared subscription (switching on after the permission prompt, switching off, every sync) runs under the Web Lock `kibo-push` (`withPushLock`, plain call without `navigator.locks`) and re-reads the subscription inside it, so tabs can't end one another's subscription; the service worker stays registered (it holds nothing and does nothing without a subscription); the hourly run (`purgeStaleSubscriptions` in `src/lib/push/subscriptions.ts`) deletes subscriptions with `failureCount ≥ 3` and 30 days without success, and those whose `lastVisitAt` and `coalesce(lastSuccessAt, createdAt)` are both older than `PUSH_SUBSCRIPTION_IDLE_DAYS` (180, `src/lib/limits.ts`); the `Topic` header is no board id but `pushTopic`: HMAC-SHA256 of the board id and endpoint (RFC 8030 replaces messages only within one subscription; this way a push service can't tell which endpoints follow the same board), base64url, cut to 32 characters, keyed by `pushTopicKey` (HKDF-SHA256 of the VAPID private key's `d`, label `kibo push topic v1`; stable as long as the subscriptions, which a new key pair ends anyway), computed per delivery; the app icon's number (`src/lib/push/unseen.ts`): each subscription has `seenAt` (its creation time at first), the count per endpoint and Kita is the current notes on the push-enabled boards it is subscribed to created after that board's `seenAt`, capped at `BADGE_MAX` (99), `unseenCounts` in one grouped query; `push.sync` returns it as `unseen`, and with the `seen` a board page sends (its board and `until`, the newest point up to which it shows every note: its server time or the newest note the server has sent it since, as long as no gap is left — `loadedUntil` in `src/composables/use-note-pager.ts`, which a note the page pinned itself doesn't move and which waits after a restarted list until older pages reach it again; `BoardApp`'s `newestSeen`, read through the getter `seen.until` for every sync) it first moves that board's `seenAt` forward to `min(until, now)` (`markBoardSeen`, scoped like the bells, never backwards, written only when a current note created after `seenAt` and up to that point hangs there, so notes the page hasn't loaded keep counting); the board page syncs again (`recount` from `usePushBells`) whenever its „Neu“ mark moves — after `loadNewest`, which `pinNote` runs after its own post (so the poster's note doesn't count, yet notes pinned elsewhere in between do until shown; `notes.create`'s `ownEndpoint` only keeps the notification away) and the worker's new-notes message asks for; `push.unsubscribe` returns `unseen` after the delete; `usePushBells` hands a number to `onUnseen` only from the badge step started last (`latestOnly` in `src/lib/board/push-client.ts`), so a late answer can't overwrite a newer one; the dispatcher sends the count per recipient as the top-level `app_badge` string of the Declarative Web Push message (where WebKit reads it, not inside `notification` as the WebKit blog's example shows); the pages set the icon through `useAppBadge` (`src/composables/use-app-badge.ts`, `showAppBadge` in `src/lib/board/push-client.ts`, `navigator.setAppBadge`/`clearAppBadge`), cleared without a subscription or permission (on the Kita page also without a public key), `public/sw.js` the same from `app_badge`, both feature-detected; a paused Kita's pages have no island and leave the icon as it was; subscribing locks the `kita_link` row (`FOR KEY SHARE`) and the board row (`FOR NO KEY UPDATE`), so it can't outlive a renewal it raced with, and the cap per board stays. `boards.setPushEnabled` drops a board's subscriptions (`src/lib/board/mutations.ts`), `boards.renewKitaLink` those of every board of the Kita. Each Kita has one manifest at `/k/<kitaToken>/manifest.webmanifest` (`id` = `start_url` = `scope` = `/k/<kitaToken>/`, the Kita's name, the shared icons), linked from every `/k/` page, so adding a board page to the home screen installs the Kita; after a renewal parents remove the icon and add the new link. `public/sw.js` is registered with scope `/k/` and shows the notifications; their `navigate` is `/k/<kitaToken>/<boardId>/` (the dispatcher reads the Kita token with the board), title `Brett „…“`.
- The documentation lives in `docs/` as plain Markdown that GitHub renders as it is: `docs/README.md` (table of contents), `docs/fuer-kitas/` (short usage pages, German, „Brett“) and `docs/selbst-hosten/` (running an instance, spam rules). ## Development

Setup: `cp .env.example .env` (set `BETTER_AUTH_SECRET`), `bun run db:up`, `bun run db:migrate`.

After changing tables: `bun run db:generate`. After changing better-auth plugins: `bun run auth:generate`, then `bun run db:generate`.

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and `astro dev logs`.

## After edits

Always run these and fix all issues:

1. `bun run lint` – oxlint, type-aware (tsgolint)
2. `bun run typecheck` – `astro check` + `vue-tsc --noEmit`
3. `bun run fallow` – fallow audit of changed files (dead code, duplication, complexity); verdict must not be `fail`
4. `bunx prettier --write <changed files>`

`bun run check` runs lint, typecheck and a prettier check in one go. For whole-project passes use `bun run fallow:dead`, `fallow:dupes`, `fallow:health`. Config lives in `.fallowrc.jsonc`; shadcn-vue components are excluded there.

## Deployment

How an instance is run is documented once, in **`docs/selbst-hosten/`** (one
page per topic, `ueberblick.md` first) — keep operational facts there, not
here. What matters while changing code:

- `Dockerfile` (`runtime` and `migrate` targets; the runtime image carries `server.mjs`, `instance-config.mjs` and `dist/admin.mjs`; the documentation is compiled into `dist/`, so `docs/` must stay in the build context — see `.dockerignore`), `deploy/` (compose, Traefik
  example, `backup.sh`, `update.sh`, legal templates) and `.github/workflows/`
  (`ci.yml` is the gate, `docker.yml` calls it and pushes to GHCR).
- The image is domain-independent: nothing is read at build time, everything
  instance-specific comes from the environment. Keep it that way.
- `scripts/migrate.mjs` is the entry point of the migration image: drizzle-orm's
  migrator, not the drizzle-kit CLI, because the CLI exits 1 without ever saying
  why. `bun run db:migrate` stays as it is for local work.
- `scripts/server.mjs` is the container entry point: it starts the standalone
  server with `ASTRO_NODE_AUTOSTART=disabled` and hands the `http.Server` to
  the bundle through `Symbol.for('kibo.httpServer')`, which is how SIGTERM can
  drain requests before the pool closes.

## Fallow local gate

Before any `git commit` or `git push`, run `fallow audit --format json --quiet --explain --gate-marker agent`. If the verdict is `fail`, fix the reported findings before retrying. Treat JSON runtime errors like `{ "error": true, ... }` as non-blocking.

Audit defaults to `gate=new-only`: only findings introduced by the current changeset affect the verdict. Inherited findings on touched files are reported under `attribution` and annotated with `introduced: false`, but do not block the commit. Set `[audit] gate = "all"` in `fallow.toml` to gate every finding in changed files.

For non-skill agents, treat the task map below as the local onboarding source: run the listed fallow command before destructive edits, before commits, and before pull request handoff.
